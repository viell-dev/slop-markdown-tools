# mdrefine 0.2.0

The first stable release of Markdown Tools. npm package: `mdrefine`; executable:
`mdtools`. Requires Node.js 22.12 or newer. Install or upgrade with:

```sh
npm install --save-dev --save-exact mdrefine@0.2.0
```

Changes below are relative to `0.2.0-rc.2`. When upgrading from an earlier
version, read the [0.2.0-rc.2](0.2.0-rc.2.md) and [0.2.0-rc.1](0.2.0-rc.1.md)
notes as well. From this release on, npm's `latest` tag names the newest stable
release, and release candidates no longer move it.

## What a stable release means here

Version numbers now describe an interface: the commands, their options and exit
codes, the JSON report, the configuration, the library's exports and types, and
the plugin contract. Before 1.0, a minor release such as 0.3.0 may change them
and says how in its notes; a patch release such as 0.2.1 fixes defects. The
wording of messages, formatting output that changes because a defect is fixed,
and speed are not part of the interface. Only the newest release line receives
fixes. [Versions and compatibility](../releases.md#versions-and-compatibility)
has the details.

## Check before upgrading

Most of this release fixes defects that were found by running the tool on
Windows. Three changes can alter what an existing setup does:

- **Read-only files.** `format --write` no longer replaces a read-only file on
  Linux and macOS. When a file that would change may not be written, or its
  folder does not let the tool create the replacement, nothing of the batch is
  written, the file gets an `engine/unwritable-file` error, and the exit status
  is 2. Make the file writable, or pass `--exclude` for it.
- **A failure while writing** no longer stops the batch. The file is reported
  with `engine/unwritable-file`, the other files are written, and the exit
  status is 2.
- **Documents that start with a byte order mark** are linted and formatted
  correctly. Such a document could be refused before, or get findings in the
  wrong places, and now gets the findings and edits of the same text without the
  mark.

Configurations of `0.2.0-rc.2` are accepted unchanged, and documents without a
byte order mark are formatted the same.

## Byte order marks

Some editors and tools, many of them on Windows, write the invisible character
U+FEFF at the start of a UTF-8 file. The parser skipped it but the rules did
not, so every position was one character off: `lint` reported findings in the
wrong places and missed others, and `format` refused the document or, where the
semantic check could not tell, deleted the blank line below a first heading. The
mark is now set aside before the rules run and kept in the formatted output.
Diagnostics count it in their offsets, so that their edits apply to the text as
given, and give the first visible character as column 1
([PR #174](https://github.com/viell-dev/slop-markdown-tools/pull/174)).

A JSON or JSONC configuration file may start with the mark too; it was rejected
as invalid JSON. Windows PowerShell 5.1 writes one with
`Set-Content -Encoding UTF8`.

## Files that cannot be written

`format --write` replaces each changed file with a new file written beside it.
When that failed for one file, the command stopped with the system's message,
which named an internal temporary file, after writing the files before it and
without writing those after it
([PR #177](https://github.com/viell-dev/slop-markdown-tools/pull/177)):

- **Before writing anything**, the tool checks that each file it is about to
  change may be written and that the file's folder lets it create the new file.
  A file that fails gets an `engine/unwritable-file` error, such as
  `The file may not be written (EACCES: permission denied); no file was written.`,
  and nothing of the batch is written, as for a document that cannot be read.
- **A read-only file is refused on every platform.** Windows refused it before,
  and Linux and macOS replaced it. Version control systems such as Perforce keep
  files read-only until they are checked out, and generated files are often
  read-only.
- **A failure that the check cannot foresee**, such as another program holding a
  file open on Windows, a file changed on disk during the run, or a full disk,
  is reported for that file in the same way, and the other files are still
  written.

The summary line adds `; 1 could not be written`, and the JSON report carries
the diagnostic in the file's entry.

## Locked files on Windows

Windows lets a program lock a file so that no other program may read it. A
locked document, link target, or configuration file stopped every command with
`EBUSY: resource busy or locked`. Such a file is now handled like one the tool
is not permitted to read: a selected document gets `engine/unreadable-file` and
the others are processed, a link to a heading in it is reported as
`Fragment could not be checked`, and a locked configuration file is reported in
the tool's words
([PR #177](https://github.com/viell-dev/slop-markdown-tools/pull/177)).

## Documentation

- The CLI guide says how to read from stdin in PowerShell, which has no `<`
  operator and changes text that it pipes into a program
  ([PR #182](https://github.com/viell-dev/slop-markdown-tools/pull/182)).
- The release documentation describes versions and compatibility and the release
  procedure for stable versions.
- The declaration of `defaultDialect` and the testing guide were brought up to
  date ([PR #184](https://github.com/viell-dev/slop-markdown-tools/pull/184)).

## Compatibility and verification

For library hosts:

- `parse` returns a document whose `source` starts after any byte order marks at
  the start of the text, where the tree's positions count from, as before.
  `lint` and `format` report positions in the text as given. `0.2.0-rc.2` kept
  the mark in `document.source` while the positions skipped it.
- A source loader given to `createWorkspace` that throws an error with the code
  `EBUSY` marks the file as unreadable, like `EACCES` and `EPERM`.

In the JSON report, an entry of `skipped` can have the code `EBUSY`, and a
file's diagnostics can carry the new rule ID `engine/unwritable-file`.

Runtime dependencies are unchanged. Development tools were updated, among them
ESLint 10.13.0, Vitest 5.0.5, and Prettier 3.9.10, and so were the GitHub
Actions that the workflows use. The Release workflow publishes a stable version
under `latest` and marks its GitHub release as the latest one; prereleases no
longer need `latest` moved by hand.

The tests of files and directories that may not be read now also run on Windows,
through access control lists, and so do the tests of linked directories, through
junctions
([PR #179](https://github.com/viell-dev/slop-markdown-tools/pull/179)). The
release was checked with 914 automated tests on Linux and Windows and with the
installed package on all three CI targets.

Known limits are those of `0.2.0-rc.2`: GitHub accepts an escaped `\$` as the
start of a formula and the tool does not; a workspace root inside a vault cannot
check links to notes outside it; one document needs about 70 to 130 times its
size in memory while it is parsed; and a single paragraph of 100 kB or more that
is full of inline constructs parses slowly. See
[design and limitations](../design.md) for the detailed boundaries.

Three accepted feature requests are planned for a later minor release: an opt-in
rule for blank lines around headings and lists
([#166](https://github.com/viell-dev/slop-markdown-tools/issues/166)),
formatting a selected part of a document through the library
([#165](https://github.com/viell-dev/slop-markdown-tools/issues/165)), and a
library export of the command line's file discovery
([#167](https://github.com/viell-dev/slop-markdown-tools/issues/167)).
